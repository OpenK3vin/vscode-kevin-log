# GitHub & GitHub Actions Conventions

Conventions for branching, pull requests, workflows, and secrets in this repo.
These apply to all contributors and to the automation bots.

---

## 1. Branch model

| Branch | Purpose | Who pushes here |
|---|---|---|
| `main` | Releasable. Every commit here _may_ trigger a release. | Bots only (Changesets version PR merge, `sync-dev` backfill). |
| `dev` | Integration. CI must be green before anything reaches `main`. | Bots only (via `sync-dev`). Manual pushes only for emergency fixups, never for features. |
| `feature/*` | New capabilities. | Contributors, branched off `dev`. |
| `fix/*` | Bug fixes. | Contributors, branched off `dev`. |
| `chore/*` | Tooling, CI, dependencies, docs. | Contributors, branched off `dev`. |
| `hotfix/*` | Emergencies that can't wait for the normal dev cycle. | Contributors, branched off `main`. |

**Rules:**

- Never commit directly to `main` or `dev` — always go through a PR.
- Branch names use lowercase kebab-case after the prefix: `feature/my-feature`, not `feature/MyFeature`.
- Delete the branch once the PR is merged. GitHub can do this automatically via repo settings.

### Hotfix path

1. Branch `hotfix/<name>` off `main`.
2. PR directly into `main`.
3. Immediately after merge, `sync-dev.yaml` will back-merge `main` → `dev` automatically. Confirm it succeeded; resolve any conflicts manually if the auto-merge fails.

## 2. Branch protection

Both `main` and `dev` must have the following ruleset applied (Settings → Branches → branch ruleset):

- **Require a pull request before merging** — no direct pushes.
- **Require CI status checks to pass** — at minimum `build-and-test` from `ci.yaml`.
- **Block force pushes.**
- **Block branch deletion.**
- **Required approvals: 0** for solo maintainers — GitHub does not allow self-approval, so any non-zero value will deadlock your own PRs.

### Bot bypass

`sync-dev.yaml` pushes directly to `dev` using `GITHUB_TOKEN`. For this to succeed, add a bypass actor to the `dev` branch ruleset:

- Ruleset → Bypass list → **GitHub Actions** (scoped to `dev` branch only).

Without this bypass, the protection rule will reject the bot's push just as it would reject yours.

## 3. Pull requests

### Targeting

| Source branch | Target branch | Notes |
|---|---|---|
| `feature/*`, `fix/*`, `chore/*` | `dev` | Normal flow. CI + changeset check run. |
| `hotfix/*` | `main` | Emergency only. Skips `dev`. `skip-changeset` label recommended unless it warrants a changelog entry. |
| Changesets "Version Packages" PR | `main` | Bot-authored. Never manually edit this PR. |

### Title format

Use the [Conventional Commits](https://www.conventionalcommits.org/) format:

```
<type>(<optional scope>): <short description>
```

Common types: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `ci`.

Examples:
- `feat: add array destructuring detection`
- `fix: log placement in multi-line function signatures`
- `chore: bump actions/checkout to v4`
- `ci: add concurrency group to release workflow`

### Changeset requirement

Every PR into `dev` **must** include a changeset file (generated by `yarn changeset`) unless the `skip-changeset` label is applied. The `changeset-check` job in `ci.yaml` enforces this automatically.

Use `skip-changeset` for PRs that have no user-visible effect: docs edits, CI config changes, internal refactors that don't change behavior.

Write the changeset description for a **user**, not a fellow contributor:
- ✅ `Fix log placement inside multi-line function signatures`
- ❌ `Refactor tryFunctionParameter to handle multiline params`

## 4. CI workflow (`ci.yaml`)

Triggers on:
- Every PR targeting `main` or `dev`.
- Every push to `dev`.

### Jobs

#### `build-and-test`

Runs on every trigger. Steps in order:

1. `actions/checkout@v4`
2. `actions/setup-node@v4` — Node 24.
3. `corepack enable` — required before any Yarn Berry command, so CI uses the exact version pinned in the repo and fails loudly if the lockfile is stale.
4. `yarn install --immutable` — not `yarn install`. `--immutable` fails hard if `yarn.lock` is out of sync instead of silently updating it.
5. `yarn lint`
6. `yarn compile`
7. `yarn test:unit`

#### `changeset-check`

Runs on PRs into `dev` only, skipped if the PR carries the `skip-changeset` label. Fails if no new file was added under `.changeset/` relative to the base branch.

### Concurrency

The `ci.yaml` uses:

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

This cancels a superseded run on the same branch/PR as soon as a newer commit is pushed. Do not remove the concurrency block.

## 5. Release workflow (`release.yaml`)

Triggers on every push to `main`.

### What it does

- If pending changeset files are present → Changesets action opens (or updates) a **"chore: version packages"** PR against `main` that bumps `package.json` and updates `CHANGELOG.md`.
- If no pending changesets (i.e., the version PR was just merged) → the action runs `yarn release`, which builds the `.vsix` and publishes to both VS Code Marketplace (`VSCE_PAT`) and Open VSX (`OVSX_PAT`).

### Build once, publish everywhere

The artifact is built once per release run and the same file is published to both registries. Never add a separate build step per registry.

### Concurrency

```yaml
concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false   # intentionally false; never cancel a release in flight
```

### Required secrets

| Secret | Used by | Where to set |
|---|---|---|
| `GITHUB_TOKEN` | Changesets action (PR creation, push) | Auto-provided by GitHub |
| `VSCE_PAT` | VS Code Marketplace publish | Settings → Secrets → Actions |
| `OVSX_PAT` | Open VSX publish | Settings → Secrets → Actions |

Add all secrets before the first real release. A missing secret causes the publish step to fail, not the setup step, so the failure may appear confusing.

## 6. Sync workflow (`sync-dev.yaml`)

Triggers on every push to `main`. Merges `main` into `dev` automatically so `dev` never permanently drifts behind `main`.

```bash
git merge origin/main --no-edit
git push origin dev
```

**Important:** Bot-authored pushes made with the default `GITHUB_TOKEN` do not trigger other workflows (GitHub's built-in loop prevention). This is expected — the push to `dev` will not re-trigger `ci.yaml`. If you need CI to run on `dev` after a sync, push a real commit.

If the auto-merge ever fails due to a conflict, resolve it manually with a regular PR from a `fix/sync-conflict` branch into `dev`, then re-run the sync.

## 7. GitHub Actions general rules

- **Pin action versions to a major tag** (`actions/checkout@v4`), not floating (`@main`) or un-versioned. Major tags offer a balance between stability and security patches.
- **Never log secret values.** The release workflow's debug step logs only the _length_ of `OVSX_PAT`, not its value — follow this pattern for any new secret diagnostics.
- **Don't chain bot-commit → workflow trigger.** Commits made by `GITHUB_TOKEN` do not fire other workflows. If you need a downstream workflow to run, use an explicit `workflow_dispatch` or a separate PAT (with awareness of the security implications).
- **Workflow permissions should be minimal.** Only grant `contents: write` and `pull-requests: write` to workflows that actually need them (release, sync). The CI workflow needs no extra permissions.
- **Name your steps.** Every `run:` step should have a `name:` — it makes the Actions log readable at a glance.
- **Use `concurrency` in every workflow** — with `cancel-in-progress: true` for CI/preview workflows, and `cancel-in-progress: false` for release/publish workflows.

---

## 8. Labels

| Label | Used by | Purpose |
|---|---|---|
| `skip-changeset` | `changeset-check` job | Bypass the changeset requirement for PRs that have no user-visible effect (docs, CI). |

Create this label in Issues → Labels before it's needed. A workflow condition referencing a label that doesn't exist silently evaluates to `false`, which can lead to confusing behavior.

---

## 9. Org-level vs. repo-level Actions settings

If the repo is under a GitHub organization:

- Org-level **Actions → General → Workflow permissions** overrides repo-level settings and greys out the repo-level control until fixed at the org level.
- Only org **owners** (not members) can change org-level settings. If the org settings page isn't visible to you, you're a member.
- Fix org-level policy first, then set repo-level to "Read and write permissions" + "Allow GitHub Actions to create and approve pull requests".
